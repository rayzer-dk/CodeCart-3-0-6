# Lost content URLs — Build 2.0.2

Before enabling, make a complete website and database backup. This is an optional CodeCart core feature, disabled by default. Open Reports → Lost URLs (404), enable and save. Viewing requires the existing report/online access permission; changing settings, statuses or redirects requires design/seo_url modify permission. No additional branch or standalone module is required.

## What is collected

Only actual HTML HTTP 404 responses to GET storefront requests are considered. JSON, AJAX, HEAD/POST, assets, API/checkout/account paths and common scanner probes are excluded. Declared bots do not create addresses; their requests only increase a separate bot counter for already discovered addresses. A plausible browser User-Agent is a heuristic, not proof of a human.

The default Needs attention view contains new addresses with at least two browser-like requests, or a referral from the store, recognized search engine or social site. Doubtful contains other single requests. Referrals can be forged; do not create redirects automatically. Inspect the address and content before deciding to restore a product/article, ignore the record or redirect it.

Records contain the missing path, safe content route/IDs where relevant, browser-like and bot counts, first/last dates, last referral path, store and language. All other query parameters, referral queries and fragments are discarded. No IP, full User-Agent or permanent visitor identifier is retained. Counts are requests, not unique people. Same-session repeats within 60 seconds count once; a short bounded session map holds only hashes and timestamps.

## Storage, cleanup and OFF

Records and redirect rules use permanent InnoDB utf8mb4 tables `<prefix>codecart_lost_url` and `<prefix>codecart_lost_url_redirect`. Tables are provisioned idempotently only on explicit enabling. No DDL runs while opening settings or handling a storefront request. OFF stops recording, redirects and cleanup before accessing working services or the database. The read-only report and enable settings remain available; disabling retains data and rules.

Each store retains at most 5000 addresses. One daily `codecart.lost_url.cleanup` task is registered in the shared scheduler on enabling. Retention is configurable: 30, 60 or 90 days since the last request. Default is 60 days and safe mode: cleanup deletes up to 500 old records per execution only if ignored, fixed or doubtful; useful unresolved addresses remain. Explicit All mode deletes any journal records older than the selected age, including unresolved useful ones, and requires confirmation in the settings form. All redirect rules remain in both modes. At capacity, new addresses wait until space is available; existing records can still accumulate counts.

Configure one regular server launch using the command shown in System → Scheduler, normally `php /absolute/store/path/cli.php cron:run`. In Mirohost, set Minutes `*/5`, Hours `*`, Days of month `*`, Months `*`, Days of week `*`, then the actual command separately. Compatible internal tasks are added in CodeCart. Independent third-party cron commands still need their own server configuration. The visitor heartbeat cannot guarantee execution when there is no traffic.

## Manual redirects

Rules return 301 and accept only terminal ASCII SEO slugs: no domain, full path, surrounding slash or `.html`. Rules are store/language-specific and preserve configured native language prefixes. The target must have one unambiguous content SEO URL in that same store/language. Existing source SEO URLs, redirect chains, cycles, external targets and equal source/target are rejected. Before use, inspect the target storefront page: a SEO table entry alone cannot guarantee a third-party content entity is still published.

At runtime, a restored source SEO URL takes precedence over its old rule; removal of the target SEO URL also stops the rule. Technical/API/AJAX paths do not redirect. Query parameters are not forwarded. Rules are paginated and can be deleted manually; deletion returns affected records to review. Source requests using numeric PHP routes are reported but cannot be redirected under the slug-only contract; restore that content or fix its original link.

## Articles and UniShop2

Missing native CodeCart blog articles were tested through actual HTTP and receive the styled 404. SEO paths are recorded independently of the theme. Safe explicit article routes include `information/uni_news_story`, `information/uni_news` and article/news IDs. Legacy OpenCart-style HTTP 404 response headers are recognized.

The original UniShop2 3.6.6.0 package was found inside `Desktop/unishop2_v3.6.6.0.zip` → `unishop2_v3.6.6.0.ocmod.zip`. Its real `information/uni_news_story` controller and `extension/module/uni_news` model were tested on isolated CodeCart with a minimal empty news schema and the CodeCart theme. An actual missing story returned legacy HTTP 404 and was recorded as an article. Full commercial-theme storefront UX and the entire theme installation are not certified by this focused test. Original third-party source is not included in this release. A theme/controller returning a soft 404 with HTTP 200 is deliberately not recorded. Errors served directly by the web server/CDN without reaching CodeCart are also outside this report.

## Verification

- PHP 8.1, 8.2 and 8.3: filter/privacy/OFF tests; changed PHP syntax checks.
- Twig: all 631 templates parsed successfully.
- Isolated MariaDB 10.11 + actual storefront/admin HTTP: explicit provisioning, settings save, 404 capture, deduplication, bot exclusions/counts, scanner exclusions, missing native article, manual 301, restored-source priority, invalid target rejection, disabling and anonymous cron denial.
- Admin runtime: report access works for a read-only group; missing SEO modify permission and invalid user_token cannot change settings.
- Retention runtime: fresh InnoDB/utf8mb4 tables and cleanup index, all six combinations (30/60/90 days × safe/all modes).
- Database/service integration: repeat provisioning, separate languages and deduplication, arbitrary `da` prefix, cross-language isolation, bounded cleanup and preservation of useful unresolved addresses, removed target prevention.
- Browser: sorting navigation works; form actions retain valid tokens. At viewport 390 px, document scroll width 375 px; only tables scroll within their wrappers (338 px wide).
- Independent review findings about live source priority, language aggregation, arbitrary prefixes and inaccessible older rules were addressed.

The workflow was compared with [SEO Backpack 404 Manager](https://www.docs.isenselabs.com/seobackpack/404_manager): detected missing addresses and manual 301 actions are useful established patterns. This implementation adds a restrained attention view and avoids automatic redirects.

Full release gates passed on PHP 8.1, 8.2 and 8.3. The subsequent retention/UniShop route refinements received targeted syntax/filter/runtime checks and Twig parsing; final CI also reruns the complete release gates.
