# Втрачені URL (404) — Build 2.0.4

[English](LOST_URLS.md) · [Усі інструкції](README.uk.md) · [Спільнота](https://t.me/+tUZNEgY3aUk4MGIy)

**Перед увімкненням створіть резервну копію файлів сайту та БД.** Відкрийте **Звіти → Втрачені URL (404)**, увімкніть моніторинг і збережіть. Типово функція вимкнена. Перегляд потребує права доступу `report/online`, зміни — права modify для `design/seo_url`.

## Перевірка відсутнього контенту

Журнал враховує фактичні HTML-відповіді HTTP 404 на GET-запити вітрини. JSON/AJAX, HEAD/POST, ресурси, API, шляхи оформлення/облікового запису та типові сканерні запити виключені. Заявлені боти не створюють записи, але можуть збільшити окремий лічильник наявної адреси.

**Потребують уваги** містить повторні запити, схожі на браузерні, або переходи з магазину, відомих пошукових/соціальних сайтів. Решта одиничних запитів — **Сумнівні**. Браузерний запит не доводить присутності людини; джерело переходу можна підробити. Лічильники показують запити, не унікальних відвідувачів; повтори в одній сесії протягом 60 секунд враховуються один раз.

Перевірте адресу та очікуваний контент. Відновіть контент, позначте запис як ігнорований або створіть ручний редирект. Автоматичних редиректів немає. Зберігаються шлях, відповідні route/ID контенту, магазин/мова, лічильники, перша/остання дата та шлях останнього джерела переходу. IP, повний User-Agent і постійний ID відвідувача не зберігаються; сторонні query-параметри та query/fragment джерела переходу відкидаються.

## Ручні редиректи

Вводьте лише кінцеві ASCII SEO slug: без домену, повного шляху, слеша на початку/в кінці та `.html`. Ціль має бути одним однозначним SEO URL контенту того самого магазину й мови. Перед збереженням перевірте, що цільова сторінка існує та опублікована.

Правила повертають HTTP 301, зберігають штатні мовні префікси й відкидають query-параметри. Наявні вихідні SEO URL, зовнішні цілі, однакові slug, ланцюжки та цикли відхиляються. Відновлений вихідний SEO URL має пріоритет над старим правилом; видалення SEO URL цілі зупиняє правило. Технічні/API/AJAX-шляхи не перенаправляються. Числові PHP route можуть потрапляти у звіт, але не підтримують редирект за правилом slug: відновіть контент або виправте посилання.

Правила мають пагінацію й видаляються вручну. Видалення правила повертає відповідні записи на перевірку.

## Зберігання, планувальник і вимкнення

Постійні таблиці InnoDB/utf8mb4 створюються лише під час явного ввімкнення. Термін — **30, 60 або 90 днів** від останнього запиту; типово **60 днів, лише сумнівні та закриті**. Безпечний режим видаляє старі ігноровані/виправлені/сумнівні записи, зберігаючи корисні невирішені адреси. Явний режим **Усі старі записи журналу** також видаляє невирішені старі записи та потребує підтвердження. **Редиректи зберігаються в обох режимах.**

Ліміт — **5000 адрес на магазин**. Після досягнення ліміту нові адреси чекають вільного місця, наявні накопичують запити. Щоденне очищення видаляє не більше **500 записів за виконання** через [спільний Планувальник](SCHEDULER.uk.md). Якщо його cron уже працює, окремий cron для журналу не потрібен.

OFF зупиняє запис, редиректи й очищення до доступу до робочої БД/сервісу. Перегляд звіту та налаштування ввімкнення доступні; вимкнення зберігає записи й правила.

## Межі сумісності

Відсутні статті штатного блогу CodeCart отримують справжній 404. Оригінальні controller/model новин UniShop2 3.6.6.0 перевірені з мінімальною порожньою схемою новин і CodeCart Theme; це не підтверджує повне встановлення або UI комерційної теми. Soft 404 із HTTP 200 та помилки вебсервера/CDN, що не доходять до CodeCart, не записуються.
