# Аудит многоязычности значений, вводимых пользователем

Дата проверки: 2026-11-18. База: ocStore 3.0.4.1 и CodeCart PRO 3.0.6 (обновление поверх существующей БД). Это аудит структуры хранения данных, форм ввода и отображения, а не проверка наличия переводов языковых PHP-ключей.

## Правило

Если значение является пользовательским текстом, который покупатель видит на выбранном языке сайта (заголовок, пояснение, предлагаемое значение по умолчанию, кнопка, сообщение магазина), интерфейс администрирования должен позволять ввести его по всем активным языкам из таблицы language. Принудительно переводить текст покупателя, заказанные товары, адреса, имена собственные и машинные идентификаторы нельзя.

## Найдено и реализовано

- `custom_field.value`: историческое общее значение для дополнительного поля покупателя. В новой схеме текстовые значения по умолчанию вводятся в `custom_field_description.default_value` отдельно для каждого языка. Если язык не заполнен, используется исходный `custom_field.value`. Проверяется `tests/custom_field_translation_smoke.php`.
- `product_option.value`: историческое общее значение для текстовой опции / текстового блока опции товара. В стандартном OpenCart у этого поля нет language_id. Добавлены `codecart_product_option_translation(product_option_id, language_id, value)`, языковые поля в редактировании товара для text и textarea, чтение в текущем языке витрины и сохранение прежнего `product_option.value` как резервного. Нестроковые типы (date, time, datetime, file), а также выбираемые варианты не изменяются. Тест: `tests/product_option_localization_smoke.php`. Требуется завершить официальный Installer UPDATE для новой ревизии схемы 46.

## Поля, для которых языковые записи уже имеются

- `product_description`, `category_description`, `article_description`, `blog_category_description`: тексты карточек и SEO-метаданные по language_id.
- `product_attribute.text`: значение характеристики товара уже по language_id; `attribute_description` и `attribute_group_description`: названия характеристик.
- `option_description` и `option_value_description`: названия опций и пункты select/radio/checkbox/image по language_id. Не следует создавать вторую систему переводов для них.
- `manufacturer_description`: описание производителя и SEO-поля по language_id; идентифицирующее название производителя намеренно общее.
- `banner_image.title`: название изображения баннера по language_id (ссылка и изображение могут быть привязаны к записи этого языка).
- `codecart_form_description`: заголовок, описание, подписи кнопок, сообщение об успехе и поля формы по language_id.
- `codecart_purchase_block` и `product_extra_tab`: тексты в клиентских блоках и дополнительных вкладках по language_id.
- `custom_field_description.name` и `custom_field_value_description.name`: названия дополнительных полей и пунктов списков уже по language_id.

## Дополнительно найдено: отдельная задача с повышенным риском

- `mail_campaign.subject` и `mail_campaign.message`: тема и тело готовой массовой рассылки пока записываются как одна языковая версия на всю кампанию. Отправщик `catalog/controller/cron/mail_campaign.php` получает эти общие поля и не выбирает перевод по `customer.language_id`. Нельзя просто добавить вкладки ввода: потребуется согласованное изменение очереди, выбора языка адресата, проверка подстановок и отписки, предпросмотра, журнала отправки и регрессионные тесты на несколько магазинов. До реализации использовать отдельные кампании по языку аудитории; автоматический перевод не выполняется.
- `codecart_notification.title/message`: системные уведомления админки хранят текст однократно; они не являются клиентским контентом витрины. Для смены языка админки нужен отдельный перевод шаблонов генератора, а не автоматическое изменение уже записанного сообщения.

## Поля, для которых общая версия корректна

- `coupon.name`, `tax_rate.name`, `layout.name`, `marketing.name/description`, `banner.name`, `codecart_form.name`: служебные названия в администрировании; не следует без анализа заменять на таблицы переводов.
- `manufacturer.name`, `country.name`, `zone.name`, `location.name`: идентификаторы / имена собственные и справочники; при необходимости транслитерация или локализованные названия рассматриваются отдельно.
- `order_product.name`, `order_option.name/value`, `order_total.title`, `voucher.message`, `review.text`: снимки заказов или текст, введённый покупателями. Нельзя переписывать задним числом при переключении языка.

## Инварианты обновления

Никакой миграцией нельзя удалять исходные `product_option.value`, `custom_field.value` или автоматически переводить существующие тексты. Чтение новых таблиц допустимо только после применения миграции. Пустой перевод означает использование прежнего общего значения. Все записи используют реальные активные языки магазина, а не фиксированные украинский/русский/английский ID. Внешние OCMOD/UniShop2 не должны требовать изменения их собственной структуры.

## Следующие проверки интеграции

Обязательны испытания на копии БД после UPDATE: сохранение/повторное сохранение товара с текстовыми опциями, существующих заказов, отображение в трёх языках, fallback, удаление опции, копирование товара, AJAX админки, а также отсутствие новых запросов к несуществующим таблицам в базе до миграции.
